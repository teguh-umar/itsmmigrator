# Changelog
## 0.1.0-rc23

- **New command `plugins:itsmmigrator:import-assets`** creates assets from a CSV exported from another GLPI's asset list (Assets > list > Export > CSV). `--file=<csv>` (keep it outside the repository), `--entity=<id>` (required, not the root), `--itemtype=` NetworkEquipment (default), Computer, Printer, Phone, Peripheral, Monitor, or the system name of an Asset definition (Storage, Security...), `--username=<login>`, `--dry-run`. The delimiter (; , or tab), a BOM and English or Indonesian column names are recognised (Name, Type, Model, Manufacturer, Serial number, Inventory number, Location, Status, Comments; other columns are ignored). An asset whose name already exists in the target entity (not in the trash) is left alone, so a second run adds nothing. Type, model, manufacturer, location (a path "A > B" becomes a tree) and status are found by name and created when missing. For an Asset definition only name, serial, inventory number, comment, manufacturer, location and status are carried (its own type and model are not). The output is counts and the file line numbers of failures: never a name, serial or address. The names are kept exactly, which is what the monitor link (`link-assets`) matches on.
- **Tests.** asset_csv_test 13; tools/staging_integration_m17.php runs the command for real on staging 2 with a synthetic CSV. Offline suite OK.

## 0.1.0-rc22

- **Fix: the asset link also works for custom assets (Asset definitions such as Wireless, Storage, Security).** In GLPI 11 every custom asset type lives in ONE table (`glpi_assets_assets`) and is told apart by its definition. rc20 searched that table once per definition without telling them apart, so one Wireless access point would have been found three times and reported as "more than one asset has that name", and not linked. Each definition is now searched only for its own rows. Core types (computers, network equipment, ...) are unchanged. Staging 2 has no asset definition yet, so nothing was wrong there; the fix matters once the Wireless/Storage/Security definitions and their assets are in.
- **Tests.** asset_linker_test 12. Offline suite OK.

## 0.1.0-rc21

- **Fetch again the attachments GLPI refused: `--retry-skipped-attachments`** (CLI flag, and a checkbox on the Run page). Until now a refused attachment (over GLPI's document size, or a file type GLPI does not accept) was mapped as skipped and never looked at again, even after the limit was raised or the type was added. With the flag, a ticket already imported that has a skipped attachment is read again (the download links are short-lived), and each skipped attachment gets another go under the limits GLPI has now. Imported: the Document is created and linked to the ticket, the map row becomes ok, and the earlier private note "Attachment not imported: <file>" is replaced by "Attachment imported later: <file>" (never a second note). Still refused: the row stays skipped and its reason is updated, no new note. Tickets with no skipped attachment are not read again. Counted as `attachments` `imported_later` / `still_refused` (`would_retry` in a dry run).
- **Tests.** attachment_retry_test 9 (wiring and rules); tools/staging_integration_m16.php runs it for real on staging 2 (2 MB limit then 50 MB, same synthetic ticket). Offline suite OK.

## 0.1.0-rc20

- **Approver not in the directory: a private note instead of a log line.** An approval whose approver is not a GLPI user (not found by the LDAP search or in the map) now leaves a private followup on the ticket: level, decision, approver name and e-mail as the source knows them, decision date and remark. It is mapped as skipped, so a later run does not add it twice. The approval is still never given to the fallback user. Tickets imported before rc20 get their notes with one `--full` run.
- **Stop on a refused key.** After 3 tickets in a row failing with HTTP 401 or 403 the run stops and says the key is the problem ("blocked, revoked or has lost its role; nothing is wrong with the tickets") instead of failing every ticket after it. A ticket that goes through resets the count. Repair with `--retry-failed`.
- **Monitor (NMS) tickets are linked to their asset.** The source keeps no asset record; the monitor writes the device name and address in the ticket ("Device: name ip Category: ..."). The importer reads the name (body first, subject as fallback) and, when exactly one asset of that name exists in GLPI (any asset type, in the ticket's entity or one it can see), adds the ticket-asset link. No asset, or more than one: a private note says what the monitor named and nothing is linked. An asset is never created. A failure there never fails the ticket. Counted as `assets` linked / already / missing / ambiguous.
- **New command `plugins:itsmmigrator:link-assets --source=<id> --username=<login> [--dry-run]`** does the same for tickets already imported (local only, no request to the source, counts only in its output).
- **Tests.** auth_streak_test 9, asset_linker_test 11. Offline suite OK.

## 0.1.0-rc19

- **Fix: an attachment GLPI would refuse no longer fails the ticket.** GLPI limits a document to its configured size (2 MB here) and accepts only the file types listed as uploadable. On the first real run a few tickets failed because one attachment was a larger zip or an unknown type (`.json`, `.cs`, `.cshtml`). The writer now checks both rules first; a file that would be refused is skipped, counted (`attachments.skipped_refused_by_glpi`), mapped as skipped (not retried every run) and named in a private followup (file name, size, reason) so it can still be fetched from the source. A generic "GLPI refused the document" is handled the same way. Tickets that failed on this are repaired with `--retry-failed`.
- **Fix: a healthy run no longer looks dead.** The run lock's heartbeat was refreshed once per page of 100 tickets; on a slow page it passed the 15-minute stale limit. It is now refreshed after every item (at most every 10 s). A gap of more than 5 minutes between two items is logged as "the computer was probably asleep" and the run goes on.
- **Tests.** attachment_rule_test 9, heartbeat_test 7. Offline suite OK.

## 0.1.0-rc18

- **Fix: a ticket with no approval is not a failed ticket.** Freshservice answers HTTP 404 (not an empty list) on `/tickets/{id}/approvals` for a ticket that never had an approval. With "Import approvals" on, rc15 to rc17 turned that into a failure of the whole ticket: on the first real run of phase 1 about a fifth of the tickets failed on it (checked read-only: ticket, conversations, tasks and time entries answer 200, only `/approvals` answers 404). A 404 there now means "no approvals"; any other error (403, network, 5xx) is still an error. Tickets that failed that way are repaired by running again with `--retry-failed` (their other children are already in place).
- **Ticket title capped at 255 characters** (the width of `glpi_tickets.name`), the `[prefix#id]` natural key kept whole, so one very long subject cannot fail a ticket.
- **Tests.** approval_test 17 (404 is none, 403 is still an error), mapping_test 31 (title cap). Offline suite OK.

## 0.1.0-rc17

- **Fix: a long category path no longer fails the run.** The map table's `src_id` was `VARCHAR(64)`, but a category's source id is its whole path (`Network > Network Security > Endpoint Protection (Anti Virus)`...) and some real paths are longer: the first real run of phase 1 failed in the categories module with "Data too long for column 'src_id'" (the dry run writes no map rows, so it could not show it). `src_id` is now `VARCHAR(255)`; a new install creates it so, and install/upgrade widens an existing column in place (idempotent, every row kept). Users (1,304 from the directory) and groups (38) written by that run stay, and a run again skips what is mapped.

## 0.1.0-rc15

- **Ticket approvals (opt-in).** Source option `import_approvals` (a tick box on the source form), run flag `--approvals` (a tick box on the Runs page). Off by default: it costs one more request per ticket (`/tickets/{id}/approvals`). Each Freshservice approval becomes a GLPI `TicketValidation`: the approver (a user already in the map: no fallback user, an unknown approver is skipped, logged and counted as `approvals.skipped_approver_unmapped`), the requester, the submission date, the decision (Requested = waiting, Approved = granted, Rejected = refused), the decision date and the remark. **One core approval step per level, named "Level N"**, so a multi-level chain keeps its order; the step is created once. An unknown status is read as "waiting", never as a decision. Each approval is mapped (`approval`), so a second run adds nothing. A dry run asks for nothing.
- **Directory lookup survives long runs.** `GlpiLdapLookup` opens a fresh connection every 250 searches and, when a search fails, reconnects once and retries before the directory is switched off for the run (the real directory refused a tired connection after thousands of searches). A dry run still never imports and a matched user is still never modified.

## 0.1.0-rc14

- **Import a date range: from a date to a date.** Until now only a start existed (`import_since` / `--since`). Now there is an end too: source options `import_until` and `import_date_basis`, CLI `--until` and `--date-basis=updated|created`, and From / Until / Date-by fields on the source form and the Runs page. A date alone as the end means the whole day (23:59:59 UTC). Empty form fields mean "not given", so the source options apply; a flag wins over an option; a start after the end is refused.
- **Two readings of "the date of a ticket".** `updated` (default): the ticket's last update time, the clock the Freshservice list is ordered by; the reader **stops** at the first ticket past the end date (no wasted reading). `created`: the day the ticket was opened; the source cannot filter by it, so the list is read from the start date and tickets outside the range are left out one by one (counted as skipped, not failed); it cannot stop early and is slower.
- **A range-limited run never moves the watermark** (an end date, or the created reading), because it has not seen every newer ticket; a creation-day run always re-reads from its start date and ignores the watermark. The end-reached note is logged.
- **Tests.** `tests/date_range_test.php` (25 checks) and additions to `source_test.php`; `tools/staging_integration_m14.php` (15 checks, staging only, own entity and source, synthetic server, created two days before updated): end date by update (40 tickets, one request, watermark untouched), flags over options, creation-day range (24 tickets, no early stop), second run idempotent, no end date still moves the watermark, empty range succeeds.

## 0.1.0-rc13

- **Windowed reading past Freshservice's 30,000 ticket cap.** One list query returns at most 300 pages of 100 tickets, oldest update first. The ticket reader used to stop with an error at page 301; the real account's import window (since 2025-01-01, and also since 2026-01-01) is larger than 30,000. When the last servable page is full, the next window now starts at the update time of the last ticket seen; the cursor is `w:<UTC time>:<page>`, the engine just keeps asking for the next page. Windows overlap by the tickets of one second (read twice, the second read is a no-op because the ticket is mapped). A window made entirely of one update second cannot advance: the reader moves one second on and logs a note (counts and a timestamp, never data). The log announces each window. The **watermark moves only after the last window**, and a failed window fails the run and leaves it alone.
- **Import in phases: source option `import_since`** (a date; a field in the source form, validated; kept in the source options next to the category list). It is the floor of a phase: with no watermark the run starts there; later runs read from the watermark minus 2 h but never below it; `--full` and `--retry-failed` read from it (not from 2010) and an explicit `--since` still wins. A wider later phase is "lower the date, run with Read everything": what is already mapped is skipped.
- **Tests.** `tests/windowing_test.php` (15 checks) against a synthetic Freshservice with 65,430 tickets and a 250-ticket cluster straddling the cap: every ticket read, never a page beyond the cap, overlap at most one second's tickets, ascending order, the exact-cap and under-cap cases, the same-second guard terminating, small-cap exact numbers, cursor parsing. `tools/staging_integration_m13.php` (16 checks, staging only, its own entity and source, a synthetic server with a cap of one page): a failing window fails the run and keeps the watermark, the next run resumes and finishes (230 tickets, each once, 3 windows), the watermark moves only then, a delta run starts 2 h before it, `import_since` and the wider later phase, a category-filtered run across windows leaves the watermark alone. 458 offline checks.

## 0.1.0-rc12

- **A dropped connection no longer fails a long import.** Reading the whole Freshservice account takes many minutes and hundreds of requests; on the real account a connection reset and a connect timeout each killed a read in the middle. `FreshserviceClient` now repeats a request that failed on the network (up to 4 times, waiting 2, 4, 8, 16 s); only network failures are repeated, never a refusal or a configuration error, and every request is a GET so repeating is safe.
- **Finding, not yet handled: Freshservice returns at most 30,000 tickets per list query** (300 pages of 100). A statistics read of the real account stopped exactly at that cap: the 30,000 oldest tickets by update time (2019 to 2021, 85 % Incident, 15 % Service Request, all Closed but 5). The adapter stops with a clear error at page 301; a full import therefore needs windowed reads (a new `since` from the last update seen) which is not built yet. The old tickets also use an older category tree than the current one (for example "Software", "Hardware", "Email" at the top), so a category filter has to name those too.

## 0.1.0-rc11

- **Freshservice HTML-escapes plain-text names; they are now decoded.** The real category tree carries entities (for example `... &amp; ...`), and the ticket's own `category` fields do the same. Left as is, GLPI would have received categories, groups and users with `&amp;` in their names, and a category filter typed with `&` would never match. The adapter now decodes category and choice words, ticket subjects, group names and user names, and the category filter decodes what the administrator types as well, so `&` and `&amp;` are the same thing. Pinned by tests.

## 0.1.0-rc6

- **Source watermark (spec §8.4).** The newest `updated_at` of the last complete, successful run is stored on the source. The next run reads tickets from the watermark **minus 2 hours** (clock skew, tickets updated while the last run was reading); with no watermark it reads everything. It moves only after a real run (not a dry run) that read the tickets module to its end (not cut by `--limit`) and ended `success` or `partial`; a fetch error makes the run `failed` and leaves it alone; it never moves backwards. `--full` ignores it; `--retry-failed` and `--recreate-missing` also read everything, because a failed or missing ticket can be older than the watermark (the map makes re-reading harmless); an explicit `--since` wins over all of these. The Runs page has a "Read everything" box and the CLI a `--full` option. Pure rules (`Engine::effectiveSince()`, `Engine::watermarkToWrite()`) are unit-tested; the whole path is tested on staging 2 (12 checks).
- **Freshservice group membership.** Members are read from the group (`agent_ids` or `members`, fetched per group when the list does not carry them) as `agent:<id>`. `GroupWriter` adds a `Group_User` row only for a user that is mapped `ok`, only when the row does not exist, and only into a group the plugin created or matched in the target entity; a group matched in a parent entity gets members only when the source option `add_members_to_matched_groups` is on (off by default). Tested on staging 2: skipped, needs_review and unknown users are never added, a re-run does not add twice, the option works. The field names are from the documentation and unverified.
- **Staging tools made safe on a staging GLPI that holds a real source.** The tools used to create their test source with `Source::add` (refused when an active source already exists on the adapter) and to delete maps and runs without a source filter. They now insert their own source row directly, use test-only ids (a tag prefix) and delete only rows of their own source id. Found when a real source was entered on staging 2 while the tools were running.
- Fixtures: `groups.json`, `group_302.json`. Tests: 277 offline.
- **Open items.** Freshservice field names, the category choices shape, `resolution`, `stats` and the group member key are from the documentation and unchecked against real data (the read-only key is now on staging 2: next is recording scrubbed responses and a `--dry-run --limit=50`); no LDAP test against a bound directory; ServiceDesk Plus, the update mode and the read-only guard (M4) are not built.

## 0.1.0-rc2

- **M2: the engine core, still without a source adapter.** Nothing can be imported yet (the Freshservice adapter is M3); this build adds and tests the machinery every adapter will use.
- **One active source per adapter (orchestrator decision, 2026-11-18).** The maps key stays `(source, src_type, src_id)` as spec §3 has it, so `Source` refuses a second active source on the same adapter and says which one to deactivate first. Changing the key to include `sources_id` is a schema change, made only if two sources of one adapter are really needed.
- **`MapRepository`**: lookup by source item, by GLPI item, by `origin_ref`; `begin()` writes the `in_progress` row and, on a lost race on the unique key, returns the other runner's row; `markOk/Failed/Skipped/Orphan/NeedsReview`; `decide()` is the spec §5 rule 1 table (create / resume / skip / retry).
- **`Lock`**: the global single-runner lock. A `running` row in `runs` is the lock (a web run spans many requests), a file lock only makes check-and-insert atomic, a heartbeat per batch proves the owner is alive. A heartbeat older than 15 minutes is stale but still blocks until forced; a live run is never aborted from outside. The refusal names source, runner and start time.
- **`Engine`**: modules in dependency order (users, groups, categories implemented; kb, assets, tickets, problems and changes are reported "not built yet"), `--limit`, dry run, `Engine::$writing` flag for the future TicketGuard, lock released in `finally`, counters stored on the run row. The source watermark is not advanced yet (it belongs to the ticket modules, M3/M5).
- **Writers**: `UserWriter` (e-mail on all addresses, alias domains second, then login; ambiguity -> `needs_review` listing both candidates; a matched user is never modified; local user only with `create_missing_users`, inactive and flagged "Imported from ..." with the leak guard; `assign_profiles` none / requester_only / all adds only the exact missing Profile_User row), `GroupWriter` and `CategoryWriter` (match what the target entity can see: its own rows plus recursive rows of ancestor entities, nearest first; create in the target entity with `is_recursive = 0`; members only for mapped users, and only into a parent's group when `add_members_to_matched_groups` is on). Resume and retry reuse the GLPI item already recorded in the row.
- **LDAP lookup (spec §4a step 3) is not built.** `LdapLookupInterface` is in place, the engine runs without an implementation and logs once that the step was skipped. It needs a verified `AuthLDAP` import call and an LDAP server to test against.
- **`plugins:itsmmigrator:purge`** works: it drops the three plugin tables (or one source's map rows with `--source`), never touches migrated GLPI data, and does nothing without `--confirm`. `run` and `verify` still refuse.
- `tests/` and `tools/staging_integration_m2.php` stay in the repository but are no longer in the zip. The tool runs the engine against a throwaway entity tree with a fake adapter on **staging only** (45 checks: matching, isolation, idempotency, resume, retry, lock, leak guard).
