# Changelog
## 0.1.0-rc12

- **A dropped connection no longer fails a long import.** Reading the whole Freshservice account takes many minutes and hundreds of requests; on the real account a connection reset and a connect timeout each killed a read in the middle. `FreshserviceClient` now repeats a request that failed on the network (up to 4 times, waiting 2, 4, 8, 16 s); only network failures are repeated, never a refusal or a configuration error, and every request is a GET so repeating is safe.
- **Finding, not yet handled: Freshservice returns at most 30,000 tickets per list query** (300 pages of 100). A statistics read of the real account stopped exactly at that cap: the 30,000 oldest tickets by update time (2019 to 2021, 85 % Incident, 15 % Service Request, all Closed but 5). The adapter stops with a clear error at page 301; a full import therefore needs windowed reads (a new `since` from the last update seen) which is not built yet. The old tickets also use an older category tree than the current one (for example "Software", "Hardware", "Email" at the top), so a category filter has to name those too.

## 0.1.0-rc11

- **Freshservice HTML-escapes plain-text names; they are now decoded.** The real category tree carries entities (for example `... &amp; ...`), and the ticket's own `category` fields do the same. Left as is, GLPI would have received categories, groups and users with `&amp;` in their names, and a category filter typed with `&` would never match. The adapter now decodes category and choice words, ticket subjects, group names and user names, and the category filter decodes what the administrator types as well, so `&` and `&amp;` are the same thing. Pinned by tests.

## 0.1.0-rc10

- **The run now says HOW users were matched.** Besides the main counters, `plugins:itsmmigrator:run` prints a detail line for users: `matched_by_email`, `matched_by_login`, `matched_by_directory_existing_user` (the directory knows the person and they already are a GLPI user), `directory_would_import` (dry run) or `directory_imported` (real run), and `skipped_no_match`. Counts only, never a name or an address. Tested on staging 2 (a dry run reports email 1, would-import 1, skipped 1, imports nobody and writes no map row).

## 0.1.0-rc9

- **Category picker on the source form.** On a saved source, "Show the categories of this source" lists the source's category tree (one read-only GET of the form listing: paths only, no ticket, no user, no counts), with a filter box; clicking a path adds it to "Import only these ticket categories". The list goes to the logged-in administrator's page and nowhere else: `ajax/categories.php` is POST only, needs the config right with Update (it uses the stored key), is CSRF-checked by GLPI on the header, discards anything printed, writes nothing and logs nothing. Checked over HTTP on staging 2 against the real source: 442 paths, 3 levels, 3 s, nothing written, no key in any answer; GET 405, no CSRF header 403.

## 0.1.0-rc8

- **Import only chosen ticket categories (early-phase scope).** The source form has a box "Import only these ticket categories" (one path per line, `Hardware` or `Hardware > Laptop`, case and spacing ignored, a path includes everything below it), stored in the source options as `ticket_categories`; `plugins:itsmmigrator:run --category="..."` (repeatable) overrides it for one run. A ticket outside the list is skipped **before any map lookup or write**: no map row, no GLPI ticket, so widening the list later imports it. A ticket with no category is left out while a filter is on. The category module creates only the chosen branches and their parents. **A filtered run never moves the watermark** (it has not seen every ticket). Tested offline (21 checks) and on staging 2 (flag, source option, widening, category tree, watermark).
- Why a run shows many "skipped" users: a source user that matches no GLPI user (by e-mail, login, then the directory) is skipped when `--create-missing-users` is off; their tickets then use `--fallback-user`. It is a count, not an error.


## 0.1.0-rc7

- **The adapter now matches REAL Freshservice answers.** Scrubbed responses were recorded from a real account on 2026-11-18 with `tools/fs_record.php` (GET only, a handful of requests, a 1 s pause; the API key is read from the encrypted source row inside the process; every name, e-mail, subject, body, note, URL, id and free text is replaced in memory before a file is written, and the raw answers are never stored). Findings, all fixed and covered by `tests/freshservice_real_test.php` against `tests/fixtures/freshservice-real/`:
  - **The resolution is `resolution_notes_html` / `resolution_notes` on the ticket**, not `resolution` (the first guess). It is only present on the ticket detail, with `stats` (`resolved_at`, `closed_at`).
  - **Group members are `members` (agent ids) in the group list itself**, not `agent_ids`; no per-group request is needed (agents also carry `member_of`).
  - **Status wording is the account's own:** codes 2 to 5 are Open, Pending, Resolved, Closed, but accounts add more (6 "In Progress", 7 "Waiting on Approval"). The adapter reads the labels once from the ticket form and reports a ticket by its real label; `Mapping` knows "In Progress" and guesses an unknown wording by its words ("waiting", "pending", "hold" -> Waiting; "resolved", "completed" -> Solved; "closed", "cancelled", "rejected" -> Closed) and reports it as UNMAPPED so the source's status map can set it. A dry run now lists each unmapped label once, before anything is written.
  - **Category choices** are `{id, display_id, value, nested_options}` (category, sub-category, item): the guess was right.
  - **Sub-lists answer with `meta.has_more`**: it is now authoritative for paging (Link header and "full page" remain the fallback). Requesters can have a null `primary_email` (no e-mail, not an empty one).
- **Found by the first real browser run: a dry run could import users from LDAP, and the directory warnings broke the page.** (1) `GlpiLdapLookup` ran the import call even in a dry run; a dry run now only searches and reports "would import" (tested with stubs that count import calls). (2) A directory that accepts the connection but cannot search (blank bind password) made core raise one PHP warning per user, each carrying the base DN and an e-mail address; they went to the PHP log and, for an administrator in debug mode, into the page in front of the JSON ("Unexpected token '<'"). They are now swallowed, the directory is switched off for the rest of the run, and only "directory N could not be searched" is logged. (3) `ajax/run.php` collects and discards anything printed while a batch runs; the page reports a non-JSON answer readably and **stops the run so the lock is released**. Re-run over HTTP as a debug-mode user: 8 steps, all JSON, success.
- **`plugins:itsmmigrator:run` needed `--username`, and it did not exist.** The option is core's per-command option, not global. The command now has a required `--username` and loads that user's session (rules and entity checks need one); the README and runbook said so wrongly before.
- Logs no longer carry a source group name or ticket subject (ids only).
- **Dry run against the real source (`--dry-run --limit=50`, source 33, entity 81):** users 50 fetched (3 matched, 47 would be skipped: no GLPI user and creation is off), groups 38 would be created, categories 50 (cut by the limit), tickets 50 would be created; 0 failed; no UNMAPPED label among the first 50. About 53 s, 7 GET requests per module page plus the form listing.
- Tests: 387 offline (`freshservice_real_test.php` 35, `ldap_test.php` 17, `scrub_test.php` 56). The recording tool and its scrubber are in `tools/` (not shipped); a test pins that the key is never printed, that only GET is used, and that no recorded fixture holds a real id, e-mail, URL or free text.
- **Open items.** Tasks and time entries have never been seen on a real ticket (none in the recent ones): their field names are still from the documentation. No LDAP test against a bound directory. ServiceDesk Plus, the update mode and the read-only guard (M4) are not built. A real (non-dry) run has not been done.

## 0.1.0-rc6

- **Source watermark (spec §8.4).** The newest `updated_at` of the last complete, successful run is stored on the source. The next run reads tickets from the watermark **minus 2 hours** (clock skew, tickets updated while the last run was reading); with no watermark it reads everything. It moves only after a real run (not a dry run) that read the tickets module to its end (not cut by `--limit`) and ended `success` or `partial`; a fetch error makes the run `failed` and leaves it alone; it never moves backwards. `--full` ignores it; `--retry-failed` and `--recreate-missing` also read everything, because a failed or missing ticket can be older than the watermark (the map makes re-reading harmless); an explicit `--since` wins over all of these. The Runs page has a "Read everything" box and the CLI a `--full` option. Pure rules (`Engine::effectiveSince()`, `Engine::watermarkToWrite()`) are unit-tested; the whole path is tested on staging 2 (12 checks).
- **Freshservice group membership.** Members are read from the group (`agent_ids` or `members`, fetched per group when the list does not carry them) as `agent:<id>`. `GroupWriter` adds a `Group_User` row only for a user that is mapped `ok`, only when the row does not exist, and only into a group the plugin created or matched in the target entity; a group matched in a parent entity gets members only when the source option `add_members_to_matched_groups` is on (off by default). Tested on staging 2: skipped, needs_review and unknown users are never added, a re-run does not add twice, the option works. The field names are from the documentation and unverified.
- **Staging tools made safe on a staging GLPI that holds a real source.** The tools used to create their test source with `Source::add` (refused when an active source already exists on the adapter) and to delete maps and runs without a source filter. They now insert their own source row directly, use test-only ids (a tag prefix) and delete only rows of their own source id. Found when a real source was entered on staging 2 while the tools were running.
- Fixtures: `groups.json`, `group_302.json`. Tests: 277 offline.
- **Open items.** Freshservice field names, the category choices shape, `resolution`, `stats` and the group member key are from the documentation and unchecked against real data (the read-only key is now on staging 2: next is recording scrubbed responses and a `--dry-run --limit=50`); no LDAP test against a bound directory; ServiceDesk Plus, the update mode and the read-only guard (M4) are not built.

## 0.1.0-rc5

- **M6: the web UI.** ICT Tools > ITSM Migrator now has three pages and a tab.
  - **Runs** (`plugin_itsmmigrator_run`): start a run (a **dry run is ticked by default**; an unticked box is an explicit "write"), live log and counters, a Stop button, the run that holds the lock (with a **Release stale lock** button that only frees a run whose heartbeat is older than 15 minutes), and the run history.
  - **Needs review**: source users that could not be matched without guessing, listed by GLPI login and real name (never an e-mail). The admin picks a candidate, any other GLPI user, or "No GLPI user". Only the mapping is written; the picked user is never modified. Tickets already imported keep the fallback user; later imports use the choice.
  - **External references** tab on Ticket, Problem and Change (only when the item has references): source, id in the source, link back to it built from the source's `base_url` (https only, `noopener`), how it got here, status, last change, and the "read-only mirror" banner for sync-owned items. It never reads the API key.
  - The menu lists the three pages; Sources need the config right, Runs and Needs review need the run right.
- **`ajax/run.php`, as spec §11 asks:** POST only, logged-in with the run right (Update), CSRF checked by GLPI's own listener on the `X-Glpi-Csrf-Token` header, the same global lock as the CLI and cron, **one small batch per request** (10 tickets, or 100 of the other items). It accepts only `start`, `step` and `abort` and a whitelist of typed flags. The position of the run (module, page, cursor, offset) and its flags live in the **server-side session**, so the browser holds only the run id and cannot change a run in the middle; a lost session just stops the heartbeat and the lock can be released after 15 minutes.
- **One code path for CLI and web.** `Engine::step()` moves a run forward by at most one batch; the CLI loops it with an unlimited batch, the web calls it once per request. To make that possible the adapters keep **no paging state**: `fetchPage()` takes the previous page's `cursor` (Freshservice users are agents first, then requesters, as `agents:<n>` / `requesters:<n>`). `Counters` can be rebuilt from a stored run.
- **Checked over HTTP on staging 2** with a temporary user (removed afterwards): the Sources list and form, Runs, Needs review and the PGN Suite section render without errors; the ajax endpoint answers 405 to GET, 403 to a POST without the CSRF header or with a wrong one, 400 to an unknown action, and a clear message for an unknown or unreachable source; the External references tab appears on a ticket with a map row and shows its link; the Profile rights tab lists the plugin's rights; **the API key never appears in any page or answer, and the source form shows only "Stored - leave blank to keep".** A full browser-driven run (start, many steps, finish) is covered by `tools/staging_integration_m6.php` through the same `WebRun` class, not by a browser, because it needs a reachable Freshservice.
- `tools/staging_integration_m6.php` (49 checks): flags, refusals, a dry web run in three steps, the same run for real, idempotency, limit, abort, the stale-lock button, the pages' HTML, Needs review, the tab. `tests/ui_test.php` pins the endpoint's guards in the source.
- **Test fixtures:** removed six entities left behind on staging 2 by earlier runs of the M2 tool (their cleanup matched entities by name and missed them).
- **Open items (unchanged).** Freshservice field names, the category choices shape, `resolution` and `stats` are from the documentation and unchecked against real data; no LDAP test against a bound directory; the source watermark is not advanced; Freshservice group membership is not read; ServiceDesk Plus, the update mode and the read-only guard (M4) are not built.

## 0.1.0-rc4

- **M7: `plugins:itsmmigrator:verify` works.** Read-only (a test pins that the `Verifier` never writes). It runs nine checks and exits 1 when anything is found, 0 when clean; `--source=<id>` limits it to one source. ## 0.1.0-rc3

- **M3: Freshservice import (tickets) and the CLI that drives it.** Built against fixtures written from the Freshservice API v2 documentation and tested on staging 2 with a fake adapter. **Nothing has run against a real Freshservice account yet** (open items below).
- **`FreshserviceClient`**: GET only, Basic auth `{key}:X`, https only, TLS verified, redirects not followed. 429 waits `Retry-After` (60 s if absent), up to 5 retries; 5xx backs off 1, 2, 4, 8, 16 s; a minimum gap of 0.4 s between requests keeps the rate low; the API key is never in an error message. Attachment links (pre-signed S3 URLs) are downloaded **without** the Authorization header.
- **`FreshserviceAdapter`**: users (agents first, then requesters; source ids `agent:<id>` / `requester:<id>` so the two id spaces cannot collide, secondary e-mails kept), groups, categories (tree paths from the category field's choices), tickets (always `updated_since`, default 2010-01-01; a clear error past Freshservice's 300-page cap), and per ticket: conversations, tasks, time entries, attachments, resolution and resolved/closed dates.
- **`TicketWriter`**: `[FS#id] subject` in the target entity; priority, type and status through the source's JSON maps over the spec §4 defaults; actors, group and category from the maps built by the earlier modules; followups (private flag, original date and author), tasks, worklogs (`actiontime`), solution, documents (same file = one Document, found by sha1; only the link is added); each child has its own map row, so a re-run never duplicates one; status and dates are written last with `$DB->update()`; the ticket row is `ok` only when every child succeeded, otherwise `failed` and `--retry-failed` completes it; a ticket moved by a business rule is put back in the target entity. A ticket that another source already created (map row with `origin_ref freshservice:ticket:<id>`) is **linked**, never duplicated.
- **Found on staging 2: `Ticket::add` silently drops `_users_id_*` and `_groups_id_*` when the session's active entity is not the ticket's entity**, which is always so for an import. Actors are therefore added with `Ticket_User` and `Group_Ticket` after the ticket exists.
- **`plugins:itsmmigrator:run` works** for the Freshservice adapter: `--source`, `--modules`, `--since`, `--dry-run`, `--limit`, `--retry-failed`, `--recreate-missing`, `--force-unlock`, `--create-missing-users`, `--activate-created-users`, `--fallback-user`, `--assign-profiles`, `--no-ldap-lookup`. Run it as a GLPI user with core's `--username`. It tests the connection first and prints a counter table. A dry run does not fetch ticket children (fewer API calls).
- **LDAP lookup (spec §4a step 3) is built** on GLPI 11.0.13's `AuthLDAP::searchUserDn()` and `AuthLDAP::ldapImportUserByServerId()`. The search is read-only; a person who is already a GLPI user is returned untouched and **never** passed to the import call (core's import re-activates an inactive user). An imported user gets the same leak guard as a created one. Only active directories are queried, the default first; a directory that cannot be reached or bound is skipped for the rest of the run. No host, base DN or user data is logged. **Tested with a stub and against staging's directories with blank bind passwords (degrades to "not found"); never run against a bound directory.**
- Tests: 8 offline suites; `tools/staging_integration_m2.php` (53 checks, now with the LDAP step) and `tools/staging_integration_m3.php` (36 checks: ticket, children, idempotency, resume, failed child and retry, natural-key adoption, cross-source link, isolation).
- **Open items.** (1) Freshservice field names, the category choices shape, the resolution and `stats` fields are from the docs and unconfirmed; record real responses as scrubbed fixtures once the read-only key is in. (2) The first real run is `--dry-run --limit=50` into a test entity. (3) The LDAP import is untested against a bound directory. (4) The source watermark is still not advanced. (5) Group membership is not read from Freshservice. (6) ServiceDesk Plus adapter, linking updates, TicketGuard, the run page: M4 onward.

## 0.1.0-rc2

- **M2: the engine core, still without a source adapter.** Nothing can be imported yet (the Freshservice adapter is M3); this build adds and tests the machinery every adapter will use.
- **One active source per adapter (orchestrator decision, 2026-11-18).** The maps key stays `(source, src_type, src_id)` as spec §3 has it, so `Source` refuses a second active source on the same adapter and says which one to deactivate first. Changing the key to include `sources_id` is a schema change, made only if two sources of one adapter are really needed.
- **`MapRepository`**: lookup by source item, by GLPI item, by `origin_ref`; `begin()` writes the `in_progress` row and, on a lost race on the unique key, returns the other runner's row; `markOk/Failed/Skipped/Orphan/NeedsReview`; `decide()` is the spec §5 rule 1 table (create / resume / skip / retry).
- **`Lock`**: the global single-runner lock. A `running` row in `runs` is the lock (a web run spans many requests), a file lock only makes check-and-insert atomic, a heartbeat per batch proves the owner is alive. A heartbeat older than 15 minutes is stale but still blocks until forced; a live run is never aborted from outside. The refusal names source, runner and start time.
- **`Engine`**: modules in dependency order (users, groups, categories implemented; kb, assets, tickets, problems and changes are reported "not built yet"), `--limit`, dry run, `Engine::$writing` flag for the future TicketGuard, lock released in `finally`, counters stored on the run row. The source watermark is not advanced yet (it belongs to the ticket modules, M3/M5).
- **Writers**: `UserWriter` (e-mail on all addresses, alias domains second, then login; ambiguity -> `needs_review` listing both candidates; a matched user is never modified; local user only with `create_missing_users`, inactive and flagged "Imported from ..." with the leak guard; `assign_profiles` none / requester_only / all adds only the exact missing Profile_User row), `GroupWriter` and `CategoryWriter` (match what the target entity can see: its own rows plus recursive rows of ancestor entities, nearest first; create in the target entity with `is_recursive = 0`; members only for mapped users, and only into a parent's group when `add_members_to_matched_groups` is on). Resume and retry reuse the GLPI item already recorded in the row.
- **LDAP lookup (spec §4a step 3) is not built.** `LdapLookupInterface` is in place, the engine runs without an implementation and logs once that the step was skipped. It needs a verified `AuthLDAP` import call and an LDAP server to test against.
- **`plugins:itsmmigrator:purge`** works: it drops the three plugin tables (or one source's map rows with `--source`), never touches migrated GLPI data, and does nothing without `--confirm`. `run` and `verify` still refuse.
- `tests/` and `tools/staging_integration_m2.php` stay in the repository but are no longer in the zip. The tool runs the engine against a throwaway entity tree with a fake adapter on **staging only** (45 checks: matching, isolation, idempotency, resume, retry, lock, leak guard).

## 0.1.0-rc1

- Release candidate: never pushed, no GitHub Release.
